# IS#6 銭認識 Round 2 指示: 状態誤検出の根絶と高速化 (Claude Code → Codex)

対象セッション: 019f0d1d-8003-7fa1-8b80-87cabec439b3
前提: Round 1 (docs/codex-coin-stability-brief-2026-07-09.md, docs/codex-coin-stability-plan.md) の実装は完了済み。
ユーザー報告の残問題: ①取得が遅すぎる ②状態が付いていない銭に状態の誤検出が多発。

## 現状コードから特定した原因 (事実)

`RhodesSuiCoinStatusRecognizer.cs` (2026-07-24時点):

1. **バッジ存在検出が無い**: いきなり10クラス分類を行い、採用条件は
   `overlayDifference >= 0.035` + `score >= 0.74` + `IsConfident (score>=0.72 && margin>=0.02)`。
   10テンプレとの最良一致は必ず何か返るため、銭アートの模様・光沢・ハイライトが状態に化ける。
   margin 0.02 / overlay差分 0.035 は判別力として弱すぎる
2. **探索窓が広い**: `StatusSearchLeft/Right=24, Up=56, Down=18`。窓内ベスト探索は比較回数に比例して
   偶然の高スコア (multiple comparisons) を拾う。スロット幾何が決定的なら窓は数pxで足りるはず
3. **スケール総当たり**: `StatusTemplateWidths` 6種 × 状態10種 × 色候補最大12 (`MaximumColorCandidatesPerStatus`)、
   銭側も `CoinTemplateSizes` 3種。実機は1280x720固定なのにスケールスイープしており、
   これがFP機会と処理時間の両方の主要因
4. **計測の穴**: `outputs/coin-stability/baseline-3/summary.json` は statusDenominator=0 (状態ゴールデン無し)、
   処理時間の計測も無し。今回の症状は現行の計測網に映らない

## 方針: 「存在検出を先に、分類は後。照合回数を桁で減らす」

### P1. 状態誤検出 (FP) の根絶

1. **バッジ存在ゲートを分類の前段に追加**:
   - 期待バッジ位置 (スロット幾何 + `ExpectedStatusOffset`) の小領域に限定して、
     (a) クリーン銭テンプレとの局所差分 (既存 overlayDifference をバッジ領域限定に変更)、
     (b) エッジ密度・彩度統計が「バッジあり」の分布に入るか、の2条件で存在判定
   - 存在が立証できなければ `status=none` を確定し、**10クラス分類を実行しない** (高速化を兼ねる)
2. **探索窓の縮小**: ゴールデンフレームでバッジ実位置の分布を計測し、±数px に固定。
   広窓での位置探索を廃止
3. **受理条件の非対称化**: 状態あり採用は「存在ゲート通過 AND score AND margin」の3条件。
   閾値の数値はハードコードせず P3 のスイープで決める。閾値未達は **unknown** (noneではない) として
   観測に流し、既存の known/none/unknown 合議と reducer 保護規則に委ねる
4. **ハードネガティブ集**: 実際に誤検出した「状態なしスロットのバッジ領域クロップ」を
   `tests/fixtures/sui-coins/status-negatives/` に蓄積し、スイープの制約 (FP=0) に使う

### P2. 高速化

1. **先に時間内訳を計測** (推測で最適化しない): 計測CLIに per-stage timing を追加
   (decode / anchor / coin照合 / status照合 / OCR、各照合回数カウント)。summary.json に出力
2. **存在ゲートによる分類スキップ** (P1-1と同一実装): 状態なしが大半なので状態分類コストがほぼ消える
3. **スケール総当たりの廃止**: 1280x720固定を前提に、ゴールデンから実寸を確定して
   バッジ・銭テンプレとも1スケール (±1px許容) に固定。照合回数 1/6〜1/18
4. **フレーム間引き**: スクロールパスでviewportフィンガープリントが同一なら再認識スキップ。
   往復スクロール (右往復+左往復) は片道+終端安定確認に見直せないか `is6CoinsFull` の
   scrollPasses を再検討。認識はスクロール静止後の1フレームのみ
5. **粗→精の2段照合** (P2-3で不足なら): 8x8/16x16ダウンサンプルで上位2〜3候補に絞ってから32x32精査
6. **並列化** (計測で必要と出たら): スロット独立なので Parallel.For

### P3. 校正と回帰 (閾値を経験則で決めない)

1. **ゴールデン拡充が前提**: statusDenominator=0 のまま閾値を触らない。ユーザーへの撮影依頼:
   - 状態なしの銭だけの保有銭一覧 (複数viewport)
   - 各状態 (10種のうち入手できるもの) が付いた銭を含む画面
   - 同名銭を複数所持し状態が異なる画面
   - 有効銭 1枚/2枚/3枚 の各パターン
   撮影はSukiの撮影ボタン→Frame Recordsに残る。取り込み手順を README化
2. 計測CLIに `--sweep` を追加: score / margin / overlay差分 / 存在ゲート閾値のグリッドを走らせ、
   **「ゴールデン+ハードネガティブでFP=0」制約下でFN最小・時間最小**の動作点を選ぶ。
   summary.json に状態の混同行列と timing を追加
3. 回帰契約: resultHash 3回一致 (既存) に加え、処理時間が前回baseline比 +20% を超えたら警告

### 実装順

1. 計測CLI拡張 (timing + 混同行列 + sweep) → 変更前ベースラインを baseline-4 として保存
2. P1-1 存在ゲート + P1-2 窓縮小 + P2-3 スケール固定 (このセットが本丸)
3. ゴールデン拡充の取り込み → sweep で閾値確定 → 効果測定 (baseline-5)
4. P2-4 フレーム間引き / scrollPasses 見直し
5. まだ遅ければ P2-5 粗→精、P2-6 並列化

### 制約 (再掲)

- 1280x720 / 16:9 基準。Back keyevent禁止。タップは矩形+ランダム化
- `dotnet build` / `npm run suki:test` / `npm test` を全緑維持。契約テストの仕様変更は同時更新
- unknown で既知状態を上書きしない reducer 保護規則は維持

## Codexへの依頼

1. この指示を現行実装と突き合わせ、齟齬や既に対応済みの項目があれば指摘

   read-only実行で受信した場合は、タスク分解と着手宣言のみ返し、実装はDesktop再開時に行う
3. 各段の完了時に baseline-N の summary (coin/status精度、FP数、処理時間) を報告する
