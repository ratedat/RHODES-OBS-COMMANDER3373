# 大会遠隔入力

## 3373だけで簡易公開する

通常の小規模大会では、中継サーバーを別途構築する必要はない。

1. 3373の「出力」を開く。
2. 「大会入力（簡易公開）」へプレイヤー表示名を入力する。
3. 「簡易公開を開始」を押す。
4. 表示された入力担当者URLと入力コードを担当者へ送る。
5. 終了時に「停止」を押す。

完全同梱の公開デバッグZIPには、簡易公開専用のNode.jsとcloudflaredを同梱する。
軽量公開デバッグZIPでは容量を抑えるため同梱せず、初回利用時に3373が公式配布元から取得し、SHA-256を検証して実行フォルダ下へ配置する。
どちらも利用者によるインストーラー実行、管理者権限、OCRモデルの導入は不要である。軽量版の初回利用時だけインターネット接続が必要になる。
「簡易公開ランタイムを削除」は障害調査や再取得用であり、通常は使用しない。

簡易公開のURLは開始するたびに変わり、停止または3373終了後に失効する。
Cloudflare Quick Tunnelは検証・小規模利用向けであり、稼働保証のある常設中継ではない。
常設URLや大規模大会で継続運用が必要な場合だけ、下部の「外部中継サーバー（上級者向け）」を使用する。

独自サーバーの構成、HTTPS公開、systemd登録、公開前確認は、[外部中継サーバー導入ガイド](external-relay-server-setup.md)を参照する。

### 開始できない場合

モデルの追加導入や再インストールは行わない。
3373に表示される停止段階と詳細を確認する。

- `ローカル中継サーバー起動中`: Node.jsの取得失敗、欠落、またはセキュリティソフトによる実行阻止
- `一時URL発行中`: cloudflaredの取得失敗、欠落、または実行阻止
- `公開経路確認中`: ファイアウォール、VPN、プロキシなどによるCloudflare接続阻止
- `入力画面準備中`: 一時URLは作成済みだが、セッション作成APIへ到達できない

停止段階と画面に表示された詳細をバグ報告ZIPへ含める。

## 目的

大会配信でADBを使用せず、Discord配信を確認する入力担当者がインターネット越しにラン状態を更新する。
更新は配信PCで検証した後に即時反映し、OBS出力にも同じstate更新を流す。

## 画面

入力担当画面は左右二画面型とする。

- 左: 現在のラン状態、選択済みオペレーター、秘宝、特殊値、ボス
- 右: テーマ別の入力操作と未送信の下書き
- 下: 操作履歴、反映結果、接続状態

初期公開では1セッションにつき入力担当者1名を想定する。
セッションIDを独立させ、将来は同時併走するプレイヤーごとに画面を切り替えられる構造を維持する。

入力担当者が変更した内容は、まず入力端末内の下書きへ追加する。
左側の「現在の配信状態」は送信前には変化しない。
オペレーター、秘宝、特殊値、ボスを含む必要な変更を終えた後、「変更を送信」を押すと1回の操作として配信PCへ送られ、検証成功後に即時反映される。
未送信の内容は「変更を破棄」で取り消せる。

「変更に追加」した下書きと、送信済みで結果待ちの内容は、同じ入力URLを使うブラウザー内に保存する。再読み込みしても復元されるが、まだ「変更に追加」していない入力欄の値、別端末への下書き移動、ブラウザーの保存データ削除後の復元は対象外とする。端末内へ保存できない場合は、画面に理由を表示して送信を止める。

### 通信が切れたとき・担当を交代するとき

- 送信結果を確認できない場合は、そのまま再接続を待つ。「同じ内容を再送」が表示された場合だけ、そのボタンで再送する。同じ操作として照合されるため、受理済みの内容が重複して適用されることはない。
- 「反映待ち」の間は編集と新しい送信を止める。「中継接続済み」は中継への到達を示し、配信PCでの反映完了は「反映済み」で確認する。
- 担当交代時は、前担当の送信が「反映済み」または拒否として確定したことを確認する。別端末で開いた画面にも前担当の反映待ちを表示し、結果が確定するまで次の送信を止める。
- 未送信の下書きは元の端末に残る。交代先では左側の最新の配信状態を確認してから入力する。拒否された入力は元の端末で下書きに戻るため、内容を訂正して送信できる。

### 配信PCを再起動したとき

大会入力を開始した後の保存済みラン状態は、3373を再起動しても引き継ぐ。「ランをクリア」すると、この引き継ぎも解除される。

入力セッションと接続は自動では再開しない。再起動後に保持されたラン状態を確認し、あらためて大会入力を開始して、新しい入力URLとコードを担当者へ渡す。前の入力URLに残る下書きや反映待ちは、新しいセッションには移さない。未確定の入力は現在の配信状態と照合してから必要な分だけ入力し直す。

## 接続境界

ローカルの `/api/state`、ADB、MAAFramework、ファイルパス、設定値をインターネットへ公開しない。

1. 配信PCが中継サーバーに大会入力セッションを作成する。
2. 配信PCは表示用に縮小したstateとmaster dataだけを中継へ送る。
3. 入力担当者は招待URL内で複数項目を下書きし、「変更を送信」で一括操作を送る。
4. 配信PCが一括操作を取得し、各項目をローカルmaster dataで検証してstateへ一度だけ反映する。
5. 反映後のsnapshotと結果を中継へ返す。

中継サーバーがローカルstateを直接変更することはない。

## 操作契約

遠隔入力で許可する操作は次に限定する。

- `campaign.set`: 統合戦略テーマの変更
- `run.set`: 源石錐、等級、分隊、難度Tier、演目、ランダム分隊効果
- `special.set`: 選択テーマに定義された特殊値
- `operator.set`: 招集状態と人数
- `relic.set`: 所持状態と使用済み状態
- `boss.set`: 選択テーマに定義されたボス選択
- `run.clear`: 現在ランの入力値を初期化
- `batch`: 上記操作を1件以上200件以下でまとめて適用

項目ID、値、選択肢は配信PCのmaster dataで検証する。
存在しないID、選択肢外の値、上限外の数値、現在テーマと異なる特殊値は拒否する。
`batch`内のいずれか1件が不正な場合は、全体を拒否してstateを部分更新しない。

## 認証

- `hostToken`: 配信PC専用。snapshot送信、操作取得、反映結果送信、セッション終了に使用する。
- `editorCode`: 入力担当者専用。招待URLに含め、操作送信と表示用snapshot取得だけを許可する。
- token/codeはログとOBS出力へ書かない。
- 中継を公開する場合はHTTPSと `TOURNAMENT_RELAY_ADMIN_TOKEN` を必須とし、セッション作成を管理認証で制限する。

## 保存と監査

中継サーバーはセッション単位で連番を付けた操作履歴を保持する。
各操作は `pending`、`applied`、`rejected` のいずれかになり、配信PCが確定したsummaryと時刻を記録する。
ローカル側でも既存ログへ操作ID、操作種別、結果を記録する。

配信PCで保存が完了した後に状態の読込や結果の通知が失敗した場合は、接続中のセッション内で通知を再試行する。保存済みの操作は再適用せず、通知が成功するまで次の操作へ進まない。この再試行状態はメモリ上に保持するため、アプリやセッションの再起動をまたぐ復旧は対象外とする。

入力端末は送信前に操作IDを保存し、再送時にも同じIDと内容を使う。中継はセッションが続く間、確定済みを含む操作を照合し、同じIDと内容なら既存の結果を返す。異なる内容へのIDの再利用は拒否する。新しい操作は、前の操作が確定してから受け付ける。

1セッションの操作上限は既定で500回の送信とする。一括送信は1回として数える。上限に達しても履歴と再送の照合情報は削除せず、新しい操作の受け付けを止める。続ける場合は保存済み状態を確認して新しいセッションを開始する。画面の履歴欄は直近100回を表示する。

状態の同期にはセッション内の世代番号を付け、遅れて届いた古い状態で入力担当画面が巻き戻らないようにする。外部中継を使う場合は、この保護を有効にするため配信PCのアプリと中継サーバーの両方を更新する。

配信PC側で行った手動訂正の中継への同期が一時的に失敗した場合も、接続中は再試行する。大会入力の画面更新では取得した状態を表示へ反映し、古い読込結果を保存し直して新しい入力を巻き戻すことを防ぐ。

## 公開デバッグ時の制約

- 簡易公開では3373がローカル中継と一時公開URLを管理する。
- 手動Relay接続では中継サーバーを別プロセスまたは外部サービスとして用意する。
- localhost中継は開発・同一PC確認用とする。
- 既定の待受先は `127.0.0.1:5180`。`TOURNAMENT_RELAY_HOST=0.0.0.0` などで外部待受する場合、`TOURNAMENT_RELAY_ADMIN_TOKEN` が未設定なら起動を拒否する。
- GLM/Ollama、ADB、MAA認識は遠隔入力経路に含めない。
- 同一stateに対する同時編集は初期版では扱わず、操作連番順に反映する。
