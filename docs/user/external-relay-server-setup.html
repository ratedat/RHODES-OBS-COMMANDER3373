RHODES OBS COMMANDER3373 / TOURNAMENT RELAY

外部中継サーバー導入ガイド

独自ドメインとHTTPSを使い、大会向け遠隔入力を常設運用するための手順です。

先に結論：短時間の大会や検証なら3373の「簡易公開」が適しています。独自ドメイン、常設URL、通信経路の管理が必要な場合だけ、外部中継サーバーを導入してください。

1. 構成と使い分け

外部中継サーバーは、配信PCと入力担当者の間で表示用snapshotと操作を受け渡します。ADB、MAAFramework、3373の設定ファイルを外部公開するものではありません。

配信PC3373 / HTTPS接続
公開サーバー443 TLS → loopback
Relay127.0.0.1:5180

入力担当者のブラウザーも、同じ公開URLへHTTPSで接続します。内部ポート5180はインターネットへ直接公開しません。

構成を選ぶ実例

利用場面選ぶ構成理由
2時間だけのDiscord大会。入力担当者は1人で、URLが毎回変わってもよい。3373の簡易公開VPS、独自ドメイン、HTTPS証明書を管理せずに開始できます。
毎月開催する定例大会。固定URLと運営管理下の通信先が必要。外部中継サーバー独自ドメインを使い、運営側で稼働と更新時期を管理できます。

外部中継サーバーを選んだ場合も、入力担当者へ渡すのは試合ごとに発行されるURLです。管理トークンは渡しません。

2. 現行版の制約

  • セッション、snapshot、操作履歴はプロセスのメモリだけに保持します。
  • relayを再起動すると、進行中のセッションは失われます。
  • セッションの有効期限は、最後の正常な操作から12時間です。
  • 操作履歴は1セッション最大500件、入力画面へ返す履歴は直近100件です。
  • 1リクエストの上限は8 MiBです。
  • 複数プロセス間で共有する永続ストアは未実装です。
単一プロセスで運用してください現行版はロードバランサーによる複数台分散、無停止更新、永続監査保管には対応していません。

3. 事前準備

用意するもの

  • 公開用のLinuxサーバーまたはWindows Server
  • 専用サブドメイン（例：relay.example.com）
  • HTTPS証明書を管理できるリバースプロキシ
  • Node.js v24系と3373のソース一式
  • 十分に長い管理トークン

公開デバッグ版で検証しているNode.jsはv24.18.0です。relayはNode.js標準ライブラリだけを使うため、npm installは不要です。

管理トークンを生成する

node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"

出力値はパスワード管理ソフトへ保存します。入力担当者には渡しません。

環境変数

変数推奨値用途
TOURNAMENT_RELAY_HOST127.0.0.1relayの待受先
TOURNAMENT_RELAY_PORT5180外部公開しない内部ポート
TOURNAMENT_RELAY_PUBLIC_URLhttps://relay.example.com入力担当者URLの公開基点
TOURNAMENT_RELAY_ADMIN_TOKEN生成した値セッション作成要求の認証
直接公開しないでくださいTOURNAMENT_RELAY_HOST=0.0.0.0だけでは通信を暗号化できません。relayはloopbackで待ち受け、公開側をHTTPSリバースプロキシにします。

このガイドで使う完成例

公開サーバーのIPアドレス203.0.113.10

relayの内部待受127.0.0.1:5180
3373のプレイヤー表示名第1試合 Player A

4. Linuxで常設する

ソースを配置する

sudo useradd --system --home-dir /opt/rhodes-relay --shell /usr/sbin/nologin rhodes-relay
sudo git clone --depth 1 https://github.com/ratedat/RHODES-OBS-COMMANDER3373.git /opt/rhodes-relay
sudo chown -R rhodes-relay:rhodes-relay /opt/rhodes-relay
node --version

秘密情報を分離する

sudo install -m 600 -o root -g root /dev/null /etc/rhodes-relay.env
sudoedit /etc/rhodes-relay.env
TOURNAMENT_RELAY_HOST=127.0.0.1
TOURNAMENT_RELAY_PORT=5180
TOURNAMENT_RELAY_PUBLIC_URL=https://relay.example.com
TOURNAMENT_RELAY_ADMIN_TOKEN=ここを生成した管理トークンに置き換える

systemdへ登録する

/etc/systemd/system/rhodes-relay.serviceを作成します。

[Unit]
Description=RHODES OBS COMMANDER3373 Tournament Relay
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=rhodes-relay
Group=rhodes-relay
WorkingDirectory=/opt/rhodes-relay
EnvironmentFile=/etc/rhodes-relay.env
ExecStart=/usr/bin/node services/tournament-relay/server.mjs
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target

nodeが別の場所にある場合は、command -v nodeで確認してExecStartを変更します。

sudo systemctl daemon-reload
sudo systemctl enable --now rhodes-relay
sudo systemctl status rhodes-relay
curl --fail http://127.0.0.1:5180/api/health

正常時は{"ok":true,"service":"rhodes-tournament-relay"}が返ります。

内部接続を確認する実例

サーバー内部では、リバースプロキシを通さずrelayへ接続します。

curl --fail http://127.0.0.1:5180/api/health

ここでConnection refusedになる場合は、DNSやCaddyを調べる前にsystemctl statusとjournalctlでrelayの起動失敗を確認します。

5. HTTPSで公開する

Caddyを使う場合の最小構成です。

relay.example.com {
    reverse_proxy 127.0.0.1:5180
}
  • DNSのAまたはAAAAレコードを公開サーバーへ向けます。
  • 公開側はHTTPS 443、転送先はhttp://127.0.0.1:5180とします。
  • request body上限を8 MiB以上にします。
  • 内部ポート5180はファイアウォールで外部へ開けません。
URLのquery stringをログへ残さない入力担当者URLには入力コードが含まれます。relay用ホストではquery stringを除外するか、アクセスログを無効化してください。

外部接続を確認する実例

DNSとCaddyを設定した後、配信PCなどサーバー外の端末から確認します。

curl --fail https://relay.example.com/api/health

内部確認と同じJSONが返れば、DNS、TLS、リバースプロキシ、relayまで接続できています。

続いて、管理トークンなしではセッションを作れないことを確認します。

curl -i -X POST https://relay.example.com/api/sessions \
  -H 'content-type: application/json' \
  --data '{"playerLabel":"接続確認"}'

正常に保護されている場合はHTTP 401となり、次のresponse bodyが返ります。

{"error":"中継サーバーの管理認証に失敗しました。","code":"admin_auth_failed"}
401は期待結果です管理トークンを持たない第三者がセッションを作れないことを示しています。

6. Windowsで動作を検証する

リポジトリ直下でPowerShellを開き、現在のプロセスだけに環境変数を設定します。

$env:TOURNAMENT_RELAY_HOST = '127.0.0.1'
$env:TOURNAMENT_RELAY_PORT = '5180'
$env:TOURNAMENT_RELAY_PUBLIC_URL = 'https://relay.example.com'
$env:TOURNAMENT_RELAY_ADMIN_TOKEN = '生成した管理トークン'
node .\services\tournament-relay\server.mjs

常設時は専用Windowsアカウントとサービス管理手段を用意し、relayはloopbackだけで待ち受けます。共有PCでは管理トークンをPowerShell履歴へ残さないでください。

同じPCだけで事前確認する実例

DNSとHTTPSを設定する前に、relayと3373の接続だけを1台のWindows PCで確認できます。PowerShellをリポジトリ直下で開きます。

$relayToken = Read-Host '管理トークン' -AsSecureString
$env:TOURNAMENT_RELAY_HOST = '127.0.0.1'
$env:TOURNAMENT_RELAY_PORT = '5180'
$env:TOURNAMENT_RELAY_PUBLIC_URL = 'http://127.0.0.1:5180'
$env:TOURNAMENT_RELAY_ADMIN_TOKEN = [System.Net.NetworkCredential]::new('', $relayToken).Password
node .\services\tournament-relay\server.mjs

別のPowerShellでInvoke-RestMethod 'http://127.0.0.1:5180/api/health'を実行します。

3373の項目入力例
プレイヤー表示名ローカル接続確認
Relay URLhttp://127.0.0.1:5180
Relay管理トークンPowerShellへ入力したものと同じトークン

「開始」を押してhttp://127.0.0.1:5180/input/...形式のURLが表示されれば、3373とrelayの接続は成功です。この確認だけでは外部のDNSとHTTPSを検証できないため、公開前に別端末から公開URLを開きます。

7. 3373から接続する

  1. 「出力」を開き、ローカル配信サーバーを起動します。
  2. 「大会入力」へプレイヤー表示名を入力します。
  3. 「外部中継サーバー（上級者向け）」を開きます。
  4. Relay URLへ公開HTTPS URLを入力します。
  5. Relay管理トークンへサーバーと同じ値を入力します。
  6. 「開始」を押し、入力担当者URLを本人へ個別に共有します。
  7. 別ブラウザーでURLを開き、現在のラン状態と変更反映を確認します。
  8. 大会終了時に「停止」を押し、セッションを削除します。

管理トークンは開始要求にだけ使われ、開始成功後は3373の画面から消去されます。設定ファイルには保存されません。

3373はrelayを約750ミリ秒間隔で確認します。3373を終了すると、入力内容の検証とローカルstateへの反映も停止します。

大会当日の反映実例

配信中のOBSに源石錐24個が表示され、同じタイミングで秘宝が1個増えた場面を考えます。

  1. 3373のプレイヤー表示名へ第1試合 Player Aを入力し、外部中継セッションを開始します。
  2. 運営担当者はhttps://relay.example.com/input/<session-id>?code=<6文字コード>形式のURLを入力担当者へ個別に送ります。
  3. 入力担当者は源石錐を24から31へ変更し、追加された秘宝を選んで「変更を送信」を押します。
  4. relayは変更をpendingとして保持し、3373が次の確認周期で取得します。
  5. 3373は源石錐の範囲と秘宝IDを検証し、問題がなければ一度のstate更新として反映します。
  6. 入力履歴がappliedとなり、OBSにも源石錐31個と追加された秘宝が表示されます。
不正な項目が混ざった場合複数項目のうち1項目でも不正なら全体がrejectedとなります。源石錐だけが変わるような部分反映は行いません。

8. 公開前の確認

  • https://relay.example.com/api/healthが200を返す。
  • HTTPがHTTPSへ転送される。
  • インターネットから5180番ポートへ直接接続できない。
  • 管理トークンなしのセッション作成要求が401になる。
  • 3373が生成した入力担当者URLが公開ドメインになっている。
  • 入力画面で現在値が表示され、テスト変更が3373で検証・反映される。
  • 「停止」後、同じ入力担当者URLを再利用できない。
  • プロキシログへquery stringと認証headerが保存されない。

9. トラブル対応

502 Bad Gateway
relayプロセスと127.0.0.1:5180/api/healthを確認します。Linuxではsudo systemctl status rhodes-relayを使います。
管理認証に失敗する
サーバーのTOURNAMENT_RELAY_ADMIN_TOKENと3373へ入力した値が一致しているか確認します。
入力URLがlocalhostになる
TOURNAMENT_RELAY_PUBLIC_URLと3373のRelay URLを公開HTTPS URLへ直します。
セッションが見つからない
relayの再起動、12時間の期限切れ、または「停止」の実行によってセッションが削除されていないか確認します。
URLは開くが表示が古い
3373で「現在値を同期」を押し、3373、ローカル配信サーバー、relayの接続状態を確認します。

502を切り分ける実例

外部のhttps://relay.example.com/api/healthが502でも、サーバー内のhttp://127.0.0.1:5180/api/healthが成功する場合、relayは動いています。Caddyの転送先、サービス起動順、ローカルファイアウォールを確認します。

内部のhealth checkも失敗する場合は、先にrelayの起動ログを確認します。

管理認証だけ失敗する実例

公開health checkは成功するのに3373の「開始」だけが失敗する場合、通信経路は通っています。環境変数の変更後にrelayを再起動していない、または3373へ古い管理トークンを入力した可能性を確認します。

再起動後にURLが無効になる実例

大会中にrelayを再起動すると、以前の入力担当者URLはsession_not_foundになります。3373から新しいセッションを開始し、新しいURLを入力担当者へ送り直します。

Linuxの直近ログは次のコマンドで確認できます。

sudo journalctl -u rhodes-relay -n 200 --no-pager

ログを共有するときは、管理トークン、hostToken、入力担当者URLのquery stringを削除してください。

10. 更新と安全上の注意

更新は大会が行われていない時間に実施します。relayの再起動で進行中のセッションが失われるためです。

cd /opt/rhodes-relay
sudo -u rhodes-relay git pull --ff-only
sudo systemctl restart rhodes-relay
curl --fail http://127.0.0.1:5180/api/health
  • relayをTLSなしでインターネットへ公開しません。
  • 管理トークンをURL、ソース、設定共有、Discordへ貼り付けません。
  • 入力担当者にはセッションごとのURLだけを個別に渡します。
  • 入力担当者URLを知る第三者も操作を送れるため、公開チャンネルへ貼りません。
  • relayはセッションをディスク保存しませんが、OS、プロキシ、ホスティング事業者が通常の接続情報を記録する場合があります。
漏えい時の対応新しい管理トークンを生成し、環境変数ファイルを更新してrelayを再起動します。その後、3373から新しいセッションを開始してください。
この文書は同梱されたrelay実装に基づくオフラインマニュアルです。更新後は環境変数、期限、保存方式を再確認してください。
