# 取得処理の性能検証

## 対象と実装

Avalonia/SukiのPC FramePool取得を対象とする。撮影基準は1280×720・16:9。
ADB入力の設定、OCRの倍率・ROI・しきい値は維持する。

- `RhodesRecognitionFrameWaiter` が撮影・比較・認識・待機を注入可能な境界として扱う。
  移動した画面と不動の画面を分け、不動時は固定待機時間を経過してから新たに連続確認する。
  撮影時間を含まない固定64msの猶予で確認回数が不足する問題を避ける。
- 安定したフレームの認識は一度だけ行う。待機が期限切れになった場合は追加撮影し、
  その区間を不確定として扱う。撮影が全回失敗した場合は追加撮影しない。
  後続の安定フレームだけを根拠に以前の不確実性は解除しない。
  区間の再訪を確実に対応付ける仕組みは未導入のため、不確実性の自動解除は行わない。
- `MaaOwnedImage` はnative bufferの生存中にコピーされた画素をmanaged側で所有する。
  フレームのPNGは必要時に生成し、同じフレームでは共有する。
  MAA認識・画面指紋はraw経路を使う。既存の一部カード検出器にはPNG経路を残す。
- 試行上限に達した未解決カードは「解決済み」にはしない。
  終端キャッシュはキャンペーン変更、ラン手動クリア、再接続、認識リソース再読込で消去する。
  解像度は既存キャッシュキーでも分離される。
- 別取得への認識結果キャッシュは導入しない。人数一致や知覚ハッシュ一致だけで
  昇進・アーミヤ職分・秘宝交換・スタック変化を省略しない。

## 計測の読み方

従来のスキャン証跡は個別ファイルとして保持し、操作中の`scanId`を共通化する。
`requestId`は各証跡に固有であり、認識後・候補化後・反映後の記録を上書きしない。

認識ログディレクトリの`Operations/operation-*.json`が操作全体の記録となる。
複数プロファイルの一括取得も一つの操作IDで計測する。
一時ファイルを完成させてから公開名へ移し、既存記録は上書きしない。
保存失敗は画面に通知し、その取得を速度比較に利用できないことを示す。

- `durationMs`: 操作開始から画面復帰、候補処理、待機可能な状態保存、証跡保存まで。
  最後の操作計測JSON自体の書込時間は含めない。
- `status`: `completed`、`partial`、`failed`、`cancelled`。
  画面復帰失敗、未解決の走査などを速度改善の成功サンプルに混ぜない。
- `stages`: `scan`、`restore`、`apply-and-save`、`evidence-save`など。
  親子の区間は重なるため、単純合計しない。
- `metrics`: 撮影、rawコピー、PNG生成、指紋、前処理、認識の回数と累計時間。
  スキャン証跡の`performance.scroll.steps`には、各スクロールの確認回数、移動有無、
  フォールバック理由、候補数、完了を阻害した条件を記録する。
- `resultSignatures`: 候補の意味上の値を順序に依存せず照合するダイジェスト。
  信頼度・OCR原文を除外し、職分ID、昇進、個体番号、スタック数などは含める。
  これは変更前後の一致確認であり、正解データの代用ではない。

## 実機比較手順

ゲーム操作の許可を受けてから、PC操作担当一名で直列に実施する。
新旧とも同じ全体計測を備えた検証ビルドを用意する。古い637311cの`durationMs`は
画面復帰・反映を含まないため、操作全体の比較には流用しない。

1. 各ケースのキャンペーン、ウィンドウ・解像度、撮影方式、推論設定、画面開始位置を固定する。
2. 画像と人が照合した正解一覧を保存し、入力画像と設定のSHA-256を記録する。
   OCRが出力した候補をそのまま正解として採用しない。
3. オペレーター・秘宝・思案の初回／再取得を、変更前後交互に各5回以上測る。
   所持内容が変わった試行は同一ケースの組から外す。
4. 同人数での昇進・アーミヤ職分変更、同数の秘宝交換、スタック増減、明示的な0件、
   ラン手動クリア、途中位置開始、接続変更、キャンセル、画面復帰失敗を別ケースにする。
5. 取りこぼし・誤採用・手動補正・保存を確認したうえで、中央値の短縮と最大時間の非悪化を確認する。

対応付けのJSON例（パスはこのJSONからの相対パス）:

```json
{
  "pairs": [
    {
      "scenario": "operators-first-same-state",
      "baseline": "baseline/operation-1.json",
      "candidate": "candidate/operation-1.json"
    }
  ]
}
```

```powershell
node tools/compare-recognition-performance.mjs outputs/verification/paired-runs.json
```

比較ツールはケース別に集計し、5組未満、失敗、不確定、部分計測、重複ID、
結果不一致、最大時間の悪化を合格扱いにしない。`accuracyVerified`は常にfalseで、
独立した正解一覧との照合結果は別途必要となる。

## 未解決事項と採用判断

- スタックOCRで、装飾や余分な文字を含む文字列を所持数として採用する経路を閉じた。
  スタックは数値と限定した既存バッジ接頭辞の全体を照合し、同一撮影の複数値は上限で
  除外する前に拒否する。同一撮影に重複したOCR行があっても、観測は1回として数える。
  実画像からの正しい所持数の読み取りと、既に保存された誤値の訂正は未解決。読取不能を1とは推定しない。
  スタックに依存する件数終了・復路省略・キャッシュ学習の保守的な抑止は維持する。
- 所持一覧から消えた秘宝が保存一覧に残る場合がある。
  通常の秘宝候補反映は追加式で、取得一覧から消えた秘宝を個別に外す処理がない。
  完全な取得と消失の根拠を確認して反映する契約が必要。単なる候補欠落や人数一致で削除しない。
- ゲーム内だけで始まった新規ランを画像だけで確実に同定するAPIは現状ない。
  ツール側のランクリアで無効化し、開始画像の一意性と現在走査の完全性も要求する。
- 自動テストの成功、固定画像の変換時間、実機の取得全体短縮は別の検証結果として扱う。
  実機比較と正解照合が揃うまでは、配布版の性能改善率を確定しない。
